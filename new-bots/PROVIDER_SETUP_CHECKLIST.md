# Six-bot provider setup checklist

This is a local setup guide for **market-data and paper testing only**. Put credentials in each bot's own ignored `.env` file. Do not paste secrets into chat, commit them, or reuse Discord webhooks between destinations. A configured key does not prove account entitlement, permitted data use, or successful authentication; each needs a provider-backed test. Live broker/exchange orders remain disabled.

For Futures active-contract candidate discovery, `npm run discover:day-session-draft --prefix futures` uses Databento continuous `[ROOT].v.0` definition mapping to draft the prior session's volume-ranked expiry per configured root. It checks the estimated request cost against `FUTURES_MAX_SCAN_COST_USD` first. Every resulting row remains review-only; current-session liquidity, exchange/broker specifications, margin, session, costs, catalysts, and executable quotes still require independent verification.

All six primary markets now have an independent Discord application configuration. Each uses its own `DISCORD_TOKEN` and `DISCORD_CLIENT_ID`. Forex, Futures, Options and ETFs/ETPs also require `DISCORD_GUILD_ID` and `DISCORD_CHANNEL_ID`; Stocks/Crypto retain their existing per-guild signal/result/log settings. The four new applications use only the Guilds intent and View Channel/Send Messages permissions; their guild-scoped operational commands require Manage Server and reply ephemerally. `npm run audit:discord` inventories identity configuration without printing credentials, and `npm run report:operator` separates configuration presence from observed runtime health. Registration, gateway readiness, correct-channel delivery and market-data readiness are separate checks. Webhook-only operation is retained only as an explicit legacy/supplemental path.

For all six paper portfolios, use the same account-equity basis and set the same shared `TRADING_RISK_STATE_PATH` only when the processes share one host/filesystem. `npm run report:operator` reports effective ledger-path fingerprint alignment, plus whether configured paper-equity values are consistent, partial, mismatched, invalid, or absent; it names affected bots but never prints dollar values or filesystem paths. For all six markets, fee and slippage assumptions must be numeric and non-negative; use numeric `0` only when zero is a deliberate, verified assumption. Stocks shared paper reservations require an explicit effective all-in per-share round-trip fee assumption. Blank or `null` values are missing, not free trading. Review per-trade and aggregate risk limits. `OMNIMOD_EMERGENCY_STOP` defaults to active; leave it active until the paper configuration is reviewed. Keep live-trading flags disabled. No provider setup should create a broker or exchange order route.

The shared paper ledger permanently anchors the account-equity basis at the first successful reservation. A later reservation using a different equity is blocked even if all previous orders are closed or cancelled. If the paper portfolio size changes, preserve/archive the prior ledger and deliberately configure a new shared ledger path for all six bots; do not delete or silently rebase the existing history.

After local setup, run a single scan in each bot's documented paper mode, inspect its provider/funnel diagnostics, then run multi-day paper observations. Provider authentication, feed quality, clock/calendar correctness, costs, and fills need separate evidence. Passing unit tests or seeing a nonempty API key is not that evidence.

Optional portfolio-wide paper circuits use the same `OMNIMOD_MAX_CONSECUTIVE_LOSSES` (positive integer) and `OMNIMOD_MAX_CLOSED_DRAWDOWN_PCT` (positive percentage no greater than 100) in **every** bot process sharing a ledger. Leave both unset until the limits are reviewed; blank, zero, boolean, and malformed configured values block approval. The loss-streak limit checks consecutive *closed* negative-net trades. The drawdown limit checks maximum historical closed-trade net-P&L drawdown against the ledger's anchored paper equity and stays breached after a later recovery. It excludes open/intratrade movement; daily-loss and fresh-mark gates still cover open positions. Once a configured reservation anchors these values, a bot with absent or different values cannot reserve against that ledger. An incomplete or ambiguous close sequence blocks new reservations while a circuit is enabled. Inspect `npm run report:operator` before changing settings. Changing an anchored policy requires a deliberately new paper ledger and operator review, not editing the old ledger.

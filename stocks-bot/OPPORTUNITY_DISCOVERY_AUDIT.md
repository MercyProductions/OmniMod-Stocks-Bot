The local data directory has no `guild-settings.json`, scan history, or model artifacts, and the inspected `.env` has no stock-provider credentials. ## 1. Effective universe — original static-watchlist baseline

The scanner is **not dynamic today**. A fresh guild uses the hard-coded 49-symbol `DEFAULT_WATCHLIST`; admins can edit it to a maximum of 75 symbols with `/stocks watchlist`. Each data refresh unions that list with 15 fixed market-context ETFs/index funds, then requests at most 90 symbols. The default list already contains 12 context symbols, so its exact default request set is **52 unique symbols**: 49 watchlist symbols plus `XLC`, `XLB`, and `XLRE`. `analyzeMomentum` excludes all 15 context symbols from trade-candidate screening, leaving **37 default screen instruments** before price, average-volume, and technical gates. ETFs in the 15-symbol context set are benchmark inputs, not candidates. Other manually added ETFs are not explicitly excluded.

The default list is concentrated in large, familiar U.S. equities and sector ETFs. There is no exchange filter, security-type filter, or automatic listing-status validation in the active scanner. The ticker syntax check alone does not intentionally exclude ADRs, OTC names, warrants, or preferreds; whether Yahoo returns a usable chart and whether later quote/risk gates pass determines what happens. The scanner does not guarantee those instruments are suitable. The active Alpaca `/v2/assets?status=active&asset_class=us_equity` capture runs only on an opening/manual scan when Alpaca credentials exist. It stores point-in-time additions/removals for research, but **does not populate or prune the watchlist**. Delisted/inactive names can remain in a manually maintained watchlist and simply fail data retrieval.

Thus the exact effective set in the inspected default local configuration is 52 requested symbols / 37 screened instruments. Because the production guild settings live outside this copy, the deployed count may differ (up to 90 request symbols / 75 custom watchlist names). No live production scan counts are available here.

**Superseded by later implementation:** the active code now defaults `STOCKS_DYNAMIC_DISCOVERY` to enabled. During premarket and regular sessions, when Alpaca credentials are configured and its endpoints succeed, eligible active/tradable NASDAQ/NYSE/AMEX assets seed batched snapshots and ranked screeners; up to 15 newly discovered names by default (configurable to 30) join the configured set for deep analysis. Thus 52 is the static default request-set baseline, not the current all-in candidate count. The effective wide eligible universe is provider/account-dependent and measured per scan; it cannot be stated as a constant or verified for production from this local copy. Outside supported market sessions, the configured list is used. See the dated discovery follow-ups below.

## 2. Existing scan architecture and baseline funnel

The current path is: configured watchlist + context → Yahoo history → all per-symbol indicators → rough score ranking → cross-check/enrichment of up to 16 preliminary names → price/volume and technical gates → repeated-scan confirmation → model decision → portfolio/execution risk selection → paper setup. This is **not** the requested discovery-first funnel: the full five-day 5-minute chart is fetched and intraday/daily indicators are calculated for every requested symbol before inexpensive price/volume filtering. The 1-year daily chart is reused for up to eight hours, but intraday history is refreshed on each cache miss.

| Funnel measure | Current code/default | Measured live value |
|---|---:|---:|
| Requested symbols | 52 (49 watchlist + 3 extra context) | No production scan record |
| Screen instruments after context exclusion | 37 | No production scan record |
| Price/average-volume eligible | Up to 37; defaults: price ≥ $2 and average share volume ≥ 500,000 | No production scan record |
| Technical qualified / watch-only | Score ≥ 68 plus hard gates / near-score watches | No production scan record |
| Consecutive confirmation | 2 scans by default | No production scan record |
| Model-approved | Validated BUY; rule-only disabled by default | Champion/readiness not available locally |
| Risk-approved | Fresh executable bid/ask ≤60 seconds plus spread, model-edge stress, concentration and circuit-breaker rules | No production scan record |
| New setups | At most 5/day by default, and no more than 3 open positions / 2 planned risk units | No production scan record |

The feature snapshot store already records many per-symbol technical rejection reasons, but it omits a unified stage funnel, symbols skipped before scoring (for example price/volume), provider latency/429 metrics, model-rejection reasons by stage, and scan-duration history. Existing daily diagnostics report some candidate/confirmation/model/risk counts but do not make a time-series funnel. The only local `data/` files are diagnostic fixtures, not a production tracker. Therefore historic real rejection counts cannot honestly be reconstructed.

## 3. Likely opportunity bottlenecks (ranked by evidence)

1. **Universe coverage:** 37 screened stocks by default and no market-wide candidate discovery. This is an explicit, measured code limit and the clearest opportunity-coverage bottleneck.
2. **Mandatory model cold start:** `STOCKS_ALLOW_RULE_ONLY_SIGNALS=false` by default. The v3 trainer uses after-cost completed production-paper setups, so no champion + no rule-only opt-in can prevent the very outcomes needed to train that fallback model. The v4 all-screen/counterfactual learner is the intended escape route, but requires executable point-in-time labels and independent trading days; live Alpaca bar streaming is required for routine accumulation. Whether this loop is occurring on production is **unknown** because champion files, labels, and settings are absent here.
3. **Executable quote gate:** risk approval rejects every candidate without a valid bid and ask timestamped within 60 seconds. Yahoo history, Finnhub quote, and Polygon last-trade adapters cannot satisfy that gate; in the inspected local config there is no Alpaca credential. This local setup could screen charts but could not approve a production paper entry. Deployed Alpaca credentials/stream state must be checked with `/stocks status`.
4. **Static universe and data failures:** newly active, small/mid-cap, and unusual-volume symbols outside the manual list are invisible. Failures and price/volume exclusions have no complete funnel summary.
5. **Costly work before filters:** on a cold/default refresh the code makes 52 Yahoo intraday requests and may make up to 52 daily requests (104 logical chart calls; six concurrent workers). Up to 10 names receive provider cross-checks at default settings, and optional event enrichment follows. The code has caching and bounded concurrency, but not batch discovery/bars or stage-specific timing.
6. **Strict upstream quality/risk controls:** score 68, two confirmations, model BUY, fresh quote, spread cap, stressed expectancy, unknown-correlation block, sector cap, open-risk cap, max three positions, five new setups/day, and loss breakers can all reduce alerts. They should remain intact while discovery and measurement improve.

## 5. Safe recommendations versus behavior changes

**Safe infrastructure changes:** instrument stage counts and structured rejection codes; record per-provider request attempts, status/429s, latency and available quota headers; expose admin-only diagnostics; retain a bounded scan history; add shadow-only candidate/strategy tracks; preserve snapshots and existing final risk gates. Add an Alpaca screener discovery adapter behind an explicit shadow-only/disabled-by-default switch so it cannot silently change production signals.

**Changes requiring forward paper validation:** connecting market-wide movers/actives to production candidate eligibility; changing chart/provider, feed, stale-data rules, score or technical gates; removing a model requirement; relaxing confirmation; changing position/correlation/sector/loss controls; promoting shadow strategies; treating news/fundamental features as predictive. None should be promoted based on activity or win rate alone.

Recommended staged design: (1) discovery seed from licensed provider market screeners and the refreshed active-symbol list; (2) batched current snapshot and inexpensive price/activity/gap/range filters; (3) existing full five-day/daily technical analysis on a bounded candidate set; (4) current model and unchanged strategy approval; (5) unchanged execution, portfolio, and circuit-breaker approval. Persist every stage and candidate reason. Shadow tracks should be separately tagged and paper-only, with fills, target1/2, stop, expiry, net modeled return, MAE/MFE, expectancy, drawdown, and sample/day counts.

**Baseline conclusion:** insufficient discovery breadth is confirmed. A model feedback loop and missing executable quotes are structurally credible bottlenecks, but cannot be quantified on the production host from the files available. No profitability claim is supported.

## 6. Model and stream cold-start details

The production v3 fallback model defaults to requiring 80 completed, after-cost graded paper setups before training. Because new production setups require a validated model by default, an empty champion plus rule-only disabled can create the suspected feedback loop. The v4 full-coverage research model is designed to learn from screens that were never production trades, but auto-training waits for three horizons at the configured 240-label minimum each (**720 horizon labels total**) plus per-horizon quality, independent-day, and leakage-resistant validation gates. These are code thresholds, not a claim that the deployed model currently has zero data; its artifacts are absent from this copy.

There is also a concrete coverage constraint in the default stream configuration: `ALPACA_STREAM_MAX_SYMBOLS=30`. The stream is given the configured watchlist order; its first 12 entries are context ETFs, leaving room for only the first **18 of 37** stock candidates (30 total). Thus the remaining 19 equities do not receive ongoing stream bars/quotes unless the cap/configuration or provider entitlement differs. This particularly slows complete minute-path labels for the v4 learner. The scanner may still fetch charts for all 37; the stream cap is a research-label and live-microstructure coverage issue, not proof that the other symbols are never screened.

### Premarket breakout discovery correction — 2026-09-24

The earlier scheduled premarket path did fetch Yahoo five-minute extended-hours bars and annotate the previous-20-session high, but it sourced watch rows only from the regular-session technical candidate/watch pool. That allowed regular-session gates such as score, RSI, VWAP, and short-term follow-through to suppress a genuine premarket high break before the observation publisher saw it.

The premarket publisher now has a separate discovery-only path over the fetched snapshot. It requires premarket time (04:00–09:29 ET), a fresh observation no more than 20 minutes old, data quality at least 60, price at least $2, 20-session high cleared, average daily volume at least 500,000, and at least a 1% move from the previous close. These produce up to five clearly labeled research watches. They bypass only regular-session watch qualification; they do not enter the model, confirmation, portfolio selection, or paper setup pipeline. No live entry controls were relaxed.

Synthetic feature fixtures confirm that a fresh liquid premarket break is surfaced even where regular-session candidate/watch gates reject it; stale, weak-quality, illiquid, sub-1% and non-breakout observations are rejected. The complete Stocks suite passes **117/117 tests** and `npm run check` passes. This does not establish Yahoo coverage or a live Discord post. Production behavior still depends on the configured worker running and publishing during a weekday premarket window; provider delay, extended-hours omissions and channel configuration remain deployment dependencies. This increases discovery coverage, not expected profitability.

### Optional Alpaca dynamic screener seed — 2026-09-24

The static watchlist is supplemented by an Alpaca active-asset catalog + multi-symbol snapshot stage and its `/v1beta1/screener/stocks/movers` and `/most-actives` endpoints by default when credentials are configured. During regular hours the bot fetches the active US-equity asset catalog, retains tradable NASDAQ/NYSE/AMEX names, requests snapshots in batches of 400, and keeps fresh same-session positive movers with minimum price/dollar-turnover checks. The top 50 movers and top 100 most-active symbols are combined with the snapshot candidates, and at most 15 new names by default (configurable up to 30) proceed to Yahoo chart analysis. This is a staged market-wide discovery path over Alpaca's eligible asset catalog, not a guarantee of every U.S.-listed security or of complete exchange data. Alpaca's asset list is its tradable/data-available master list; snapshot feed coverage depends on the configured feed. ([Alpaca assets](https://docs.alpaca.markets/us/v1.4.2/reference/get-v2-assets-1), [Alpaca multi-symbol snapshots](https://docs.alpaca.markets/us/reference/stocksnapshots-1), [Alpaca movers](https://docs.alpaca.markets/us/v1.4.2/reference/movers-1), [Alpaca most-active](https://docs.alpaca.markets/us/reference/mostactives-1))

`STOCKS_DYNAMIC_DISCOVERY` defaults to `true`; set it to `false` to disable. When enabled and credentials exist, an active-asset response is cached for six hours and snapshot candidates for 15 minutes. A catalog of N supported assets costs `ceil(N/400)` multi-symbol snapshot requests per refresh, plus one asset-list request per cache expiry. Regular-session refreshes also request two ranked screeners; premarket refreshes skip those session-screening calls. For example, 8,000 supported assets means 20 snapshot requests per 15 minutes (about 80/hour during a six-hour regular session), before other provider traffic. The current local code has no credentials, so the live catalog size and returned snapshot coverage cannot be measured. Calls are bounded to concurrency 3 and record attempts, HTTP failures/429s, latency, and returned quota headers. Failed snapshot batches are reported while successful batches and the configured watchlist remain usable. These names join existing downstream technical/confirmation/model/portfolio gates; no quality threshold or risk requirement is relaxed. Since the eligible candidate set changes, use forward paper validation before relying on it. No profit improvement is claimed.

The catalog currently filters to `status=active`, `tradable=true`, and exchanges NASDAQ/NYSE/AMEX. That excludes OTC, ARCA, BATS, and non-tradable catalog entries. Alpaca's asset response does not reliably identify common stock versus ETF, ADR, warrant, or preferred share, so these can remain in the list if otherwise eligible; there is no unsupported type-based exclusion heuristic. Snapshot price/volume screens and the existing quote/model/risk checks still apply. The default configured feed is IEX, which is one venue and can omit consolidated activity; select SIP/delayed SIP only if the account supports it. `/stocks diagnostics` now shows eligible catalog count, returned snapshot symbols, broad snapshot candidate count, screener count, deep-chart count, and provider errors.

Tests cover mover/active deduplication, static/context exclusion, symbol caps, authorization headers, request paths, caching, missing credentials, and partial 403 fallback. No live Alpaca screener request or Discord scan was made in this review.
